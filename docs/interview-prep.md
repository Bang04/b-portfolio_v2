## 이 문서를 쓰는 법

포트폴리오에 적힌 문장은 **주장**이고, 면접은 그 주장을 검증하는 자리다.
이 문서의 목적은 "무엇을 했는지"를 다시 적는 게 아니라, **되물었을 때 두 번째·세 번째 답까지 준비하는 것**이다.

각 항목의 구성:

| 칸 | 의미 |
|---|---|
| **예상 질문** | 실제로 나올 문장 그대로 |
| **의도** | 면접관이 이 질문으로 확인하려는 것 |
| **답변 축** | 답변에 반드시 들어가야 할 뼈대 |
| **⚠️ 꼬리질문** | 여기서 갈린다. 첫 답은 누구나 하지만 이건 못 한다 |
| **🚫 감점** | 이렇게 답하면 위의 성과까지 의심받는다 |

우선순위: **S급 = 반드시 나온다** / **A급 = 높은 확률** / **B급 = 나오면 차별화**

**의도** — 숫자를 만든 사람인지, 들은 사람인지. 그리고 React 렌더링 모델을 **원리로** 이해하는지 패턴으로 외웠는지.

**⚠️ 꼬리질문**

**🚫 감점**
- "React.memo를 씌워서 최적화했습니다" (무엇이 왜 재렌더됐는지가 빠지면 암기로 들린다)

## S3. 도메인 격리 — 5개 플랫폼 공유 셸

**근거** [portfolioData.ts:284](src/data/portfolioData.ts#L284), [:960](src/data/portfolioData.ts#L960)

**"공통 코드 수정 0건"은 이 포트폴리오에서 가장 아키텍처다운 주장이다.** 시니어 면접관이 가장 좋아할 소재이자, 가장 깊게 파고들 소재.

**예상 질문**
- "공통 코드를 한 줄도 안 고쳤다고 하셨는데, 그 규칙을 어떻게 강제하셨나요?"
- "정말 공통 셸을 고쳐야만 해결되는 요구사항이 나왔다면 어떻게 하셨을 건가요?"
- "중복을 감수했다고 하셨는데, 세 번째에 공통화한다는 기준은 어디서 온 건가요?"

**의도** — 격리가 **운이었는지 설계였는지**. 그리고 원칙을 상황에 맞게 굽힐 줄 아는지(경직된 원칙주의는 감점이다).

**답변 축**
1. 제약이 먼저 있었다 — 성능도 확장성도 아닌 **격리가 1순위 제약**
2. 접점을 라우트 등록 한 곳으로 물리적으로 제한
3. 규칙을 사람 기억이 아니라 **경로 스코프 규칙 문서 + pre-push hook**으로 외부화
4. 대가도 말한다 — 중복을 감수했고, Rule of Three를 기준으로 뒀다

**⚠️ 꼬리질문**
- **"문서와 hook은 우회할 수 있잖아요"** → ESLint `no-restricted-imports`나 CODEOWNERS 같은 **기계적 강제** 수단을 아는지. 솔직하게 "문서 수준이었고, lint 규칙으로 올리는 게 다음 단계"라고 답하는 게 낫다
- 라우트 등록 한 곳이 정말 유일한 접점인가? **빌드 설정, 공통코드(`SYS_FEAT`) 테이블, 인증/권한, 전역 스타일**은? (여기서 "아 그것도 접점이네요"가 나오면 주장이 흔들린다 — 미리 정리해 둘 것)
- 공통 셸에 버그가 있으면 어떻게 하나? 못 고치는 건가?
- 다른 네 플랫폼 팀과 협의 채널은 있었나?
- 마이크로 프론트엔드를 고려했나? 왜 안 했나?

## S5. 상태 분리 — Query / Zustand / URL / useState 🔧 정정

**근거** [portfolioData.ts:297](src/data/portfolioData.ts#L297), [:1032](src/data/portfolioData.ts#L1032)

프론트엔드 면접의 **가장 흔한 심층 질문 영역**이다. 포트폴리오가 이미 기준을 명시했으므로, 그 기준을 흔드는 질문이 온다.

**🔧 정정** — 종전에 "Zustand = 위저드 상태"로 적었으나 **위저드 폼은 `useState` 단일 소유**이고, Zustand는 **목록 화면 UI 상태(검색어·필터·페이지) 전용**이다. 그리고 "선택된 급경사지·활성 탭"은 **URL이 단일 출처**다. 즉 3분할이 아니라 **4분할**이고, 이쪽이 답으로도 더 강하다.

**예상 질문**
- "Zustand를 쓴 이유가 뭔가요? Context로는 안 됐나요?"
- "서버 상태와 클라이언트 상태를 나누는 기준이 애매한 경우는 없었나요?"
- "'현재 선택된 급경사지' 상태는 어디에 뒀나요?"

**의도** — 라이브러리 선택이 **취향인지 근거인지**. 그리고 경계 사례에서 스스로 판단할 수 있는지.

**답변 축**
- 기준은 **"이 값의 주인이 누구인가"** — 서버(Query) / 목록 화면 UI(feature 스코프 Zustand) / 지금 보고 있는 대상(URL) / 폼 입력(useState)
- **앱 전역 스토어를 만들지 않았다**는 게 핵심 결정이다. 전역 스토어는 "어디에 둘지 애매한 값"이 전부 모이는 자리가 되고, 도메인 격리와 정면으로 충돌한다
- 셀렉터 구독은 성능이 아니라 **정확성** 문제이기도 하다 (검색어 한 글자에 무관한 컴포넌트가 리렌더되지 않게)

**⚠️ 꼬리질문**
- **"선택된 항목 id는 URL에 있어야 하지 않나요?"** — 이건 **이미 그렇게 했다.** 오히려 먼저 꺼낼 카드다. "스토어에 두면 언제 비울지를 계속 관리해야 하지만, URL에 두면 새로고침·뒤로가기·링크 공유가 추가 코드 없이 동작하고 화면을 벗어나면 자연히 사라진다"까지 말할 것
- **"위저드 상태는 왜 Zustand가 아닌가요?"** — 단계 전환이 라우팅이 아니라 **같은 화면 안의 조건부 렌더**라 `useState` 하나로 값이 유지된다. 스토어를 쓰면 얻는 것 없이 "언제 비우나" 문제만 생긴다
- Context + `useReducer`로 충분하지 않았나? Zustand의 실질적 이득은?
- Query의 `staleTime` / `gcTime`은 어떻게 설정했고 근거는? (**설정값을 기억 못 하면 "기본값을 그대로 썼다"로 들린다 — 미리 확인해 둘 것**)
- URL에 상태를 두면 직렬화·파싱 비용이 생기는데, 잘못된 URL로 진입하면?

## A3. 등급 계산 — 프론트 미리보기 + 서버 확정 🔧 정정

**근거** [portfolioData.ts:380](src/data/portfolioData.ts#L380), [:948](src/data/portfolioData.ts#L948)

**🔧 정정** — 종전에 "프론트가 등급을 산정한다"로 적었으나, **확정 등급은 서버가 재계산해 덮어쓴다.** 프론트 계산은 입력 중 미리보기다. **이쪽이 훨씬 좋은 답**이므로 자신 있게 말하면 된다.

**예상 질문**
- "등급이 행정 판단의 근거가 되는 값이라고 하셨는데, 그걸 왜 프론트에서 계산하나요?"
- "순수 함수로 분리했다면 테스트 코드는 있나요?"

**의도** — 첫 질문은 **신뢰 경계(trust boundary)** 개념을 아는지 보는 것이다. 브라우저에서 계산한 값은 사용자가 조작할 수 있으므로 최종 확정값은 서버가 가져야 한다.

**답변 축**
1. **역할을 나눴다** — 프론트는 입력 중 미리보기, 서버는 제출 후 확정. 브라우저가 만든 값을 행정 판단의 근거로 삼을 수는 없다
2. 프론트 계산이 필요한 이유는 UX다 — 제출한 뒤에야 등급을 알면 조사자가 되돌아와야 한다
3. 순수 함수로 뽑은 이유는 **설명 가능성** — 입력만 주면 항상 같은 값이 나와야 "왜 D등급인가"를 답할 수 있고, 서버 결과와 어긋났을 때 어디서 갈렸는지도 짚을 수 있다

**같이 말하면 강한 한 줄** — "같은 배점 기준이 프론트와 서버 두 곳에 있으니, 한쪽만 개정되면 조용히 어긋납니다. 기준을 서버에서 내려받아 한 벌만 두는 게 다음 단계입니다." (약점을 먼저 말하는 쪽이 이긴다)

**⚠️ 꼬리질문**
- 서버 계산 결과와 프론트 계산 결과가 다르면 어느 쪽을 믿나?
- **테스트 코드는?** (§ 구조적 공백 참고 — 순수 함수라고 강조해 놓고 테스트가 없으면 아프다)
- 배점 기준이 번들에 있어 개정 시 재배포가 필요한데, 언제 서버 내려받기로 바꿀 건가?

# ⚫ 구조적 공백 — 포트폴리오에 없어서 더 물어보는 것들

## 1. 테스트 (가장 확실하게 나온다) 🔴
포트폴리오 전체에 **테스트 언급이 한 번도 없다.** 그런데 "순수 함수로 분리해서 테스트하기 좋게 만들었다"는 취지의 문장은 있다([:388](src/data/portfolioData.ts#L388)). 면접관은 이 간극을 정확히 짚는다.

- 예상: "테스트 코드는 작성하셨나요?" / "등급 계산 함수 테스트는요?" / "리팩토링할 때 안 깨진 걸 어떻게 확인했나요?"
- **권장 대응**: 없으면 없다고 말하고, **왜 없었는지(일정·조직 관행)와 무엇부터 넣을 것인지**를 말한다. 등급 계산 순수 함수는 테스트를 붙이기 가장 쉬운 대상이므로 "여기부터 시작하겠다"가 자연스러운 답이다.
- 💡 **면접 전에 등급 계산 함수 테스트를 몇 개라도 실제로 작성해 두면**, 이 질문이 약점에서 강점으로 뒤집힌다.

## 2. 협업 프로세스
`data.md` 4절에도 이미 표시된 공백 — PR 리뷰, 이슈 트래킹, Figma/Notion 협업 기록이 없다.
- 예상: "코드 리뷰는 어떻게 받으셨나요?" / "프론트 2명이면 작업 분배는?"
- 대응: 팀 규모(프론트 2·백엔드 2)에서 실제로 어떻게 나눴는지, 리뷰가 없었다면 그 대신 무엇으로 품질을 지켰는지(컨벤션 문서·hook)

## 3. 에러 처리 / 로딩 UX
포트폴리오에 거의 언급이 없다. 데이터가 많은 관제 화면인데 **네트워크 실패 시 UX**를 물으면 답할 거리가 있어야 한다.
- 예상: "API가 실패하면 화면이 어떻게 되나요?" / "전역 에러 바운더리는?"

## 4. 배포 / 운영
"운영 이관은 아직"이라고 적혀 있다([:910](src/data/portfolioData.ts#L910)). 배포 파이프라인, 환경 분리, 모니터링 경험을 물으면 경계를 명확히.

## 5. 못 한 것 3종 (가상화 / Web Vitals / 실시간)
**근거** [portfolioData.ts:1182](src/data/portfolioData.ts#L1182), [:1393](src/data/portfolioData.ts#L1393)
이미 문서에 적어 뒀으므로 **면접관은 "그럼 지금은 어디까지 아세요?"로 이어간다.** "학습 중"이라고 썼으면 진도를 말할 수 있어야 한다.
- 가상화: 왜 필요한지, `react-window`의 기본 동작 원리(윈도잉), 언제 도입할지
- Web Vitals: LCP/INP/CLS가 각각 무엇을 재는지 정도는 반드시
- 실시간: WebSocket vs SSE 선택 기준, 관제 도메인에서 어디에 쓸지

# 🟢 역질문 준비 (면접 마지막 5분)

포트폴리오의 마지막 문장이 "숫자는 어떤 것이든 근거를 설명해 드릴 수 있습니다"이므로([:1497](src/data/portfolioData.ts#L1497)), 태도의 일관성을 위해 **역질문도 구조에 관한 것**으로 준비하는 게 좋다.

- 팀에서 공통 컴포넌트/디자인 시스템은 누가 소유하고, 변경은 어떤 절차로 이뤄지나요?
- 성능 목표를 숫자로 관리하는 지표가 있나요? (있다면 무엇을 보시나요)
- 프론트엔드에서 테스트는 어느 범위까지 작성하는 문화인가요?
- 스펙이 확정되기 전에 개발을 시작해야 하는 상황이 자주 있나요? 그때 팀은 어떻게 대응하나요?
