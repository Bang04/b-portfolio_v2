## 2. 이력서용 불릿 포인트 (3~5개)

- Google Maps `AdvancedMarker`+`MarkerClusterer`로 급경사지 **160건**을 등급(A~E)별 클러스터링·시각화한 2D/3D 관제 대시보드를 구현하고, 목록-지도 간 카메라 포커스 연동 인터랙션을 설계함
- 마커 선택 변경 시 전체 재렌더링되던 구조를 `React.memo`와 `useRef` 기반 콜백 고정 패턴으로 재설계해, 선택당 리렌더 작업량을 **2,889건 → 2건**으로 축소(3D DOM 재부착·폴리곤 재계산·2D 마커 재생성 3개 병목을 동시 해소)
- `React.lazy` 기반 라우트 코드 스플리팅을 적용해 도메인 화면을 **21개 온디맨드 청크**로 분리하고, `vite build` 실측 비교(worktree 전/후 비교)로 초기 진입 번들을 gzip 기준 **3,479.82KB → 3,425.63KB(−54KB, 약 1.6%↓)**로 검증
- TanStack Query 단일 쿼리 키 구독 구조로 3곳에 흩어져 있던 mock 데이터 import를 통합해, 설정 화면 저장 시 캐시 무효화만으로 대시보드가 즉시 동기화되는 구조를 설계함
- Zustand로 전역 상태를 관리하는 6단계 신규 등록 위저드를 구현, 단계별 유효성 검증·임시저장(로컬스토리지) 복원·지도 클릭 기반 좌표 자동 입력(역지오코딩)까지 완결함

## 3. 포트폴리오 상세 설명 (문제→해결→기술→결과, 약 500자)

급경사지 관제 시스템의 종합현황 대시보드에서, 마커 선택 하나를 바꿀 때마다 지도 전체가 눈에 띄게 버벅이는 문제가 있었습니다. 원인을 추적한 결과, 3D 마커 2,889개가 매 렌더마다 DOM에 재부착되고, 폴리곤 강조 로직이 전체를 순회하며, 2D 마커도 객체 참조가 매번 바뀌어 불필요하게 재생성되고 있었습니다. "선택이 바뀌어도 실제로 달라지는 건 이전 선택 해제와 새 선택, 단 2개뿐"이라는 지점에 착안해, 마커 컴포넌트를 `React.memo`로 분리하고 콜백을 `useRef`로 고정해 참조 안정성을 확보했으며, 직전 선택 id를 ref로 추적해 델타만 갱신하도록 재설계했습니다. 그 결과 선택 변경당 작업량이 2,889건에서 2건으로 줄었고, 기존에도 존재하던 마커 클릭 지연 문제까지 함께 해소되었습니다. React, TypeScript, Google Maps API 기반이며 공통 코드는 건드리지 않고 도메인 컴포넌트 내부에서만 해결했습니다.

## 4. 우대사항 중 확인이 필요한 항목 (추가 질문)

로그에 명시적 근거가 없어 과장하지 않고 질문으로만 남깁니다:

1. **실시간 UI(WebSocket/SSE) 경험** — 급경사지 시스템은 React Query 폴링/캐시 무효화 기반으로 보이는데, 실시간 소켓 통신을 실제로 붙인 화면이 있었나요? (있다면 어떤 화면·데이터에 적용했는지)
2. **성능 분석/개선 도구(Web Vitals, Chrome DevTools) 경험** — 번들 사이즈는 `vite build` 실측으로 검증한 기록이 있는데, Lighthouse/Web Vitals(LCP, INP 등)나 DevTools Performance 탭으로 렌더링 병목을 직접 프로파일링한 사례가 있나요?
3. **가상화(virtualization) 경험** — 160~2,889건 규모 데이터를 다뤘지만, `react-window`/`react-virtualized` 같은 리스트 가상화 라이브러리를 적용한 화면이 있었나요?
4. **디자인 시스템/컴포넌트 라이브러리 "운영" 경험** — 16종 레이아웃 카탈로그를 재사용한 기록은 있는데, 이 시스템을 직접 설계·구축·문서화하거나 팀 단위로 운영한 경험인지, 아니면 기존 것을 소비만 한 것인지 명확히 해주시면 좋겠습니다.
5. **협업 방식(이슈/PR/코드리뷰, Notion/Figma 사용)** — 커밋 로그는 잘 정리되어 있지만 팀 단위 PR 리뷰나 Notion/Figma 협업 경험이 있는지는 로그만으로 확인이 안 됩니다.
6. **ESLint/Prettier/Husky/Playwright 스택 일치 여부** — `pre-push` git hook(빌드 자동검사)은 기록에 있는데, 공고가 요구하는 도구셋과 정확히 일치하는지, E2E 테스트(Playwright) 경험이 있는지 확인이 필요합니다.
